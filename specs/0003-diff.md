# 0003: Access diffs, `pageslens diff`

**Status:** shipped in 0.4.0 (PR #15). User reference: [docs/diff.md](../docs/diff.md).

Builds on the one-line entry in [mvp-spec.md](research/mvp-spec.md) ("Diff: what changed in access between two versions, in plain language") and on [0001-policies.md](0001-policies.md). Lint asks "is this configuration a known mistake?", a policy asks "does this site still meet our requirements?", and diff asks "what does this change do to who can see and change what?". It is the exhaustive picture that [0001-policies.md](0001-policies.md) leaves out on purpose: the policy holds targeted invariants, diff shows everything else that moved.

Main use: a sticky pull request comment posted by the planned GitHub Action. Second use: a local check before pushing ("what does my uncommitted edit do?").

### What the industry converges on

1. **Summary first, details folded.** A count line (Terraform, what-if), then the list, with long parts in `<details>` (tfcmt, Atlantis).
2. **Fixed change vocabulary.** `+ - ~` and a closed set of change types (Terraform, what-if). Ours: wider, narrower, neutral.
3. **Call out the dangerous direction.** Destroy warnings and red labels (tfcmt), FAIL on possible new access (AWS). For access, "wider" is the direction that needs a reviewer.
4. **Conservative when unsure.** AWS fails on "might allow new access". A change we can't prove narrower is not reported as narrower.
5. **Compare decisions, not text.** The OpenFGA CI pattern and Access Analyzer both compare what is allowed. A YAML diff is already in the PR; the value is the effective result.
6. **One comment, updated.** Infracost, tfcmt and dependency review all edit a single comment; Atlantis hides old ones. Identified by a hidden marker.
7. **Size limits are real.** GitHub rejects comment bodies over 65,536 characters (HashiCorp hit it and switched to a summary plus artifact). Atlantis splits; others link to an artifact.
8. **Exit codes for "changed" are opt-in.** `git diff --exit-code`, `terraform plan -detailed-exitcode`; dependency review fails only above a threshold. By default a diff is information, not a gate.
9. **Base versus merge base.** PR tools compare against the merge base, so commits added to `main` meanwhile don't show up reversed (Semgrep, GitHub's own three-dot PR diff).

## Design rules

- **Diff effective access, not files.** Both sides go through the same adapters, access graph and Web API surface as `docs` and `test`. A permission split in two with the same result is not an access change.
- **Closed change vocabulary.** A fixed set of change kinds, each with a fixed sentence and a fixed classification. No user configuration of what counts.
- **Conservative classification.** Wider means "may give someone access they didn't have". Anything we can't prove is narrower or neutral is wider.
- **Every line names its source.** Role, privileges, table, scope, and the permission (with file) that causes it, in the same words `test` uses for evidence.
- **Deterministic.** Sorted, no timestamps; the same inputs give byte-identical output, so the sticky comment only changes when the access does.
- **Fits a comment.** Summary first, wider changes always visible, the rest folded, a hard size cap.

## Command

```
pageslens diff <base> <head> [path] [--merge-base] [--format text|markdown|json] [--fail-on wider|any]
```

**Base comes first**, like `git diff A B`, Terraform (current → planned), `kubectl diff` (live → applied) and dependency review (`base-ref`, `head-ref`). Sentences read "head compared with base": "gained", "lost".

### Inputs

Each of `<base>` and `<head>` is a folder or a git ref:

- An existing directory is a folder. Otherwise it must resolve as a commit (`git rev-parse --verify --end-of-options <arg>^{commit}`). If it's both a directory and a ref, it's an error asking for `./<name>` (folder) or a full ref, the way git reports an ambiguous argument.
- **Two folders**: `pageslens diff downloads/before downloads/after`. Each is resolved like `lint`'s path (a `.powerpages-site` inside it, or a folder with `website.yml`). No `[path]`.
- **Two refs**: `pageslens diff origin/main HEAD [path]`. `[path]` is the site folder relative to the current directory, default `.`; it's mapped to its path inside the repository and read at each ref.
- **A ref and a folder**: `pageslens diff origin/main .` compares the committed site at `origin/main` with the working tree, so uncommitted edits show. The folder's path inside the repository is read at the ref. No `[path]`.

Reading at a ref uses git, without a checkout or worktree: `git ls-tree -r -z <commit> -- <path>` for the file list and one `git cat-file --batch` process for the contents. The adapters today read the file system directly (`listFiles`, `readYaml`, side files in `readRecordFiles`); they'd read through a small file source (list, read text) with a file-system and a git implementation. Git blobs are as committed, so `core.autocrlf` doesn't matter; the model already normalises side-file newlines.

`--merge-base` compares `git merge-base <base> <head>` with head instead of base, like `git diff --merge-base` and GitHub's PR diff. The Action passes it. Refs come from untrusted PRs, so every git call uses `--end-of-options` and an argument array, never a shell.

A side where the site folder doesn't exist (the PR adds the site, or removes it) is read as an empty site, with a note in the output: "base has no site at `portal/`; everything is new". A side that exists but fails to load is a load error, exit 2, as for `lint`.

### Matching records

- **GUIDs are the identity** (AGENTS.md). Records match by kind and GUID. File names and folders are ignored, so renamed or moved files are not changes.
- **Renames** (same GUID, new name) are neutral, shown once: `Role "Customer" renamed to "Customers"`. Later lines use the head name.
- **Layouts**: both layouts produce the same model and Dataverse GUIDs, so a classic download can be compared with a code-site download. When the layouts differ, the header says so. Model version 1 and 2 classic downloads are the same layout to us.
- **Roles that keep their name but get a new GUID** (deleted and recreated, or a site re-provisioned) are matched by name when exactly one removed and one added role share it, with a neutral note "recreated with a new id"; their grants are then compared as one role. Otherwise each is added or removed.
- **The special roles** are matched by their flag, not only by GUID: "the Anonymous Users role" and "the Authenticated Users role". Moving a flag to another role is its own change (see below).

### What counts as an access change

Each side is reduced to facts. A change is a fact that differs. The fact kinds are closed:

**1. Grants.** From each side's access graph, the effective grants, keyed by (role, table, scope, privilege), with the permissions that produce each as sources. Inherited roles on child (Parent scope) permissions are included, as in the access matrix. Permissions that aren't effective (no role, broken chain) give no grants, so fixing or breaking a chain shows up as gained or lost grants, with the cause named ("the chain under 'Contact - Self' is now complete").

| Change                                                                                        | Class                                                                                                           |
| --------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| A role gains a privilege on a table at a scope                                                | wider, unless the role already had that privilege on that table at **global** scope (global covers every scope) |
| A role loses a privilege on a table at a scope                                                | narrower, unless the role still has it at global scope (then neutral)                                           |
| Same (role, table, scope, privilege), but its contact, account or parent relationship changed | wider: it may reach other rows                                                                                  |
| Same access, different source (a permission renamed, split, merged or replaced)               | neutral                                                                                                         |

A scope change on one permission is shown as one line, "write on contact changed from contact scope to global scope", but classified by the rules above: to global is wider, from global is narrower, between two other scopes is wider (they reach different rows; scopes aren't ordered, as in the policy grammar).

**2. Web API.** From each side's Web API surface:

| Change                                    | Class                                                     |
| ----------------------------------------- | --------------------------------------------------------- |
| Web API enabled on a table                | wider; the line lists who can call it (roles with grants) |
| Web API disabled on a table               | narrower                                                  |
| Fields added, or changed to `*`           | wider                                                     |
| Fields removed, or `*` replaced by a list | narrower                                                  |

A grant change on a table where the Web API is enabled (on head) gets a suffix "(Web API enabled)" instead of a second line. Callers are listed only when the enabled state changes, so nothing is reported twice.

**3. Roles.**

| Change                                                                   | Class                                                                     |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| Role added, removed, renamed                                             | neutral (its grants are reported as grants)                               |
| A role becomes the Authenticated Users role, or the Anonymous Users role | wider (its grants now apply to every signed-in user, or to every visitor) |
| A role stops being one                                                   | narrower                                                                  |

**4. Page access rules** (not in v1, decision 4). pageslens reads them into the model but only `role-unused` uses them; no lint rule, docs section or policy statement interprets them yet. They come to diff with the M3 page work (`page-access-gap`, site map docs). The intended rule-level classification, for then:

| Change                                                | Class    |
| ----------------------------------------------------- | -------- |
| Restrict Read rule removed, or a role added to one    | wider    |
| Restrict Read rule added, or a role removed from one  | narrower |
| Grant Change rule added, or a role added to one       | wider    |
| Grant Change rule removed, or a role removed from one | narrower |

**5. Selected site settings** (in v1, decision 4). A short closed list, documented, each with a fixed direction. Starting list:

| Setting                                                              | Wider when                                                                   |
| -------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `Authentication/Registration/Enabled`, `.../OpenRegistrationEnabled` | turned on (effective value, with Power Pages defaults, as `test` reads them) |
| `Authentication/Registration/RequiresInvitation`                     | turned off                                                                   |
| `Webapi/error/innererror`                                            | turned on                                                                    |
| `HTTP/Access-Control-Allow-Origin`                                   | an origin added, or `*`                                                      |

Any other setting is out of scope: it's a text change git already shows. Server Logic, cloud flows and website access (front-side editing) come later, when the model reads them.

### Ordering

Changes are grouped wider, then narrower, then neutral. Within a group, a fixed sort key, most exposed first:

1. audience: Anonymous Users role, Authenticated Users role, then other roles by name;
2. scope: global, account, contact, parent, self (for grants);
3. table logical name; 4. privilege in the order `read, write, create, delete, append, appendto`; 5. source name.

Non-grant changes sort by their audience where they have one (enabling the Web API on a table anonymous can read sorts with anonymous), then by kind. There's no score or severity: the order is explainable from the key, and lint already has severities.

### Wording

One sentence per change, reusing the evidence wording from `src/policy/evaluate.ts` (`grantEvidence`), moved to a shared module so `test` and `diff` say the same thing:

- test: `Authenticated Users has write on contact (global scope) from "Contact - Authenticated Users Global Write"`
- diff: `Authenticated Users gained write on contact (global scope) from "Contact - Authenticated Users Global Write"`

Several privileges for the same role, table, scope and source are joined: `gained read, write`. A parent-scope grant adds `, under "<top parent>"` as `test` does, and `(inherits roles from "<parent>")` when its roles are inherited. Lost grants name the base source: `Customers lost read on incident (contact scope) from "Incident - Customers" (removed)`.

## Output

### Markdown (for the PR comment)

```markdown
<!-- pageslens:diff site=.powerpages-site -->

### Access changes

**2 wider, 1 narrower, 2 neutral** in `.powerpages-site`, `origin/main` (a1b2c3d) → `HEAD` (e4f5a6b)

#### Wider

- **Authenticated Users** gained **write** on `contact` (global scope) from "Contact - Authenticated Users Global Write" (Web API enabled)
- **Customers** gained **read** on `incident` (contact scope) from "Incident - Customers"

#### Narrower

- **Anonymous Users** lost **read** on `knowledgearticle` (global scope) from "Articles - Anonymous Read" (removed)

<details><summary>2 neutral changes</summary>

- Role "Customer" renamed to "Customers"
- "Contact - Self" renamed to "Contact - Own record" (same access)

</details>

<details><summary>Where these come from</summary>

| Change                            | File                                                                             |
| --------------------------------- | -------------------------------------------------------------------------------- |
| Authenticated Users write contact | `table-permissions/Contact-Authenticated-Users-Global-Write.tablepermission.yml` |
| ...                               | ...                                                                              |

</details>
```

- The first line is a hidden marker the Action uses to find its comment; it includes the site path so a repository with several sites gets one comment per site.
- No changes: `No access changes in .powerpages-site, origin/main → HEAD.`
- Commit SHAs are shown (short) because they are inputs, not run metadata; no timestamps, no tool version.
- **Size cap: 60,000 characters** (GitHub's limit is 65,536). When over, drop in this order until it fits: the sources table, neutral details, narrower details. Wider lines are never dropped before the others; if wider alone is too long, keep as many as fit and end with "and N more wider changes: run `pageslens diff` locally or see the JSON artifact". The counts line is always exact.

        }

```

`kind` is a closed list: `grant-gained`, `grant-lost`, `grant-rows-changed`, `grant-source-changed`, `webapi-enabled`, `webapi-disabled`, `webapi-fields-wider`, `webapi-fields-narrower`, `role-added`, `role-removed`, `role-renamed`, `role-audience-changed`, `setting-wider`, `setting-narrower` (page-rule kinds come with M3). This is what the agent skill `pr-access-review` reads.

No SARIF: a diff isn't a list of findings on lines.

### Exit codes

- **0** when the comparison ran, whatever it found. A diff is information for a reviewer (`git diff`, `terraform plan` without flags).
- **1** only with `--fail-on`: `--fail-on wider` exits 1 if anything is wider; `--fail-on any` if anything changed at all (like `git diff --exit-code`). The output is the same either way.
- **2** usage errors, an unknown ref, an ambiguous argument, a site that fails to load. The same meaning as `lint` and `test`.

Hard requirements belong in the policy (`only "Billing" can read dwcrm_invoice`), which `test` enforces. `--fail-on wider` is for teams that want every widening to need an explicit override (re-run after approval, or a label the workflow checks), like dependency review's `fail-on-severity`.

## How it fits with `lint`, `test` and the Action

|                  | lint                                    | test                                  | diff                                |
| ---------------- | --------------------------------------- | ------------------------------------- | ----------------------------------- |
| Question         | Known mistakes?                         | Still meets our requirements?         | What does this change do to access? |
| Input            | one site                                | one site + policy                     | two sites                           |
| Fails by default | on errors                               | on any failed statement               | never                               |
| PR surface       | SARIF → code scanning (new alerts only) | SARIF → code scanning, required check | sticky comment                      |

- **No overlap with "new findings only".** Code scanning already shows only alerts a PR introduces (PR #14). Diff doesn't list lint findings. It may add a short hint after a wider line that also trips a lint rule ("also reported by lint: global-write"), since that link is cheap and useful; see open questions.
- **Shared wording** with `test` (above), and a shared fact model with `docs` (the access matrix is the head side of a diff).
- **GitHub Action** (planned): runs `lint --format sarif` and `test --format sarif` (upload), then `diff --merge-base --format markdown origin/<base> HEAD <path>` and creates or updates one comment found by its marker (Infracost's `update` behaviour). It also writes the Markdown to the job summary, which works on fork PRs where the token can't comment. Needs `fetch-depth: 0` (or a fetch of the base branch) for the merge base, and `pull-requests: write` to comment. With no access changes it edits an existing comment to say so and doesn't create a new one.
- **Agent skill** `pr-access-review` reads the JSON and writes the human review: why a change might be intended, what to check.

## Implementation sketch

- `src/adapters/files.ts`: a file source (list, read) with file-system and git implementations; the adapters read through it. `src/util/git.ts`: `rev-parse`, `merge-base`, `ls-tree`, a `cat-file --batch` reader, via `spawn` with argument arrays.
- `src/graph/describe.ts`: the grant wording, moved from `src/policy/evaluate.ts`.
- `src/diff/facts.ts` (site → facts), `src/diff/compare.ts` (base facts, head facts → classified, sorted changes), `src/diff/format/{text,markdown,json}.ts`; `diff` in `src/cli.ts`.
- Tests: `test/fixtures/diff/<case>/{base,head}/` folder pairs, one per change kind and per classification rule (including scope change, inherited child roles, chain fixed, role recreated, settings, layouts mixed, missing side); a test that builds a temporary git repository to cover ref reading and `--merge-base`; Markdown and text snapshots; a size-cap test.
- Docs: `docs/diff.md` (the change kinds and their classification table, like `docs/policy.md`), README section.

## Decisions (Oleksandr, 2026-10-24)

Every recommendation below is adopted, with these notes:

- **4.** v1 covers grants, Web API, roles and the settings list. Page access rules are out of v1: nothing in pageslens interprets them yet, so they wait for the M3 page work.
- **5.** `--fail-on wider|any` is in v1, under that name.

## Open questions for Oleksandr (answered, see Decisions)

1. **Arguments.** Base first, each side a folder or a ref detected automatically (error when ambiguous), plus the ref-and-folder form for the working tree? Recommended: yes, as above.
2. **Merge base.** Compare exactly the refs given, with `--merge-base` opt-in (the Action passes it), or use the merge base by default when both sides are refs? Recommended: exact by default, like `git diff`; `--merge-base` opt-in.
3. **Classification.** Conservative "wider = may widen": scope changes between non-global scopes and relationship changes count as wider; global covers other scopes. Recommended: yes.
4. **What's in v1.** Grants, Web API and roles for sure. Also page access rules (rule-level) and the short settings list? Recommended: grants, Web API, roles and the settings list in v1; page access rules in v1 only if the rule-level wording is acceptable without computed inheritance.
5. **Exit codes.** Exit 0 by default, `--fail-on wider|any` opt-in. Is `--fail-on` the right name (dependency review uses `fail-on-severity`), and do you want it in v1 at all? Recommended: yes, both values, in v1.
6. **Comment content.** Diff only, or also a one-line lint and test status in the same comment? Recommended: diff only, plus the lint hint on wider lines; lint and test live in code scanning and checks.
7. **Neutral changes.** Show them folded (renames, same access from a different permission), or leave them out? Recommended: folded, so a reviewer can see why files changed without access changing.
8. **Size cap.** Fixed 60,000 characters with the drop order above, or a `--max-length` option? Recommended: fixed; the JSON has everything.
9. **Recreated roles.** Pair a removed and an added role with the same name (with a note), or report them as removed and added? Recommended: pair them, only when the name match is unique.
10. **Missing side.** Treat a site folder missing at one side as an empty site (everything added or removed), or exit 2? Recommended: empty site with a note, so the first PR that adds a site still gets a comment.

- Compares effective grants (with inherited child roles), the Web API (enabled, fields, callers), web roles (added, removed, renamed, recreated, built-in flag moved) and five settings read with Power Pages defaults. Records matched by GUID. Every change is wider, narrower or neutral, conservatively; most exposed first. Grant wording shared with `test` in `src/graph/describe.ts`.
- Markdown for the PR comment: hidden marker, summary first, neutral changes and sources folded, 60,000-character cap with a set drop order. Text and versioned JSON. Exit 0 by default, 1 with `--fail-on`, 2 for unusable input. A side with no site is an empty site, with a note.
