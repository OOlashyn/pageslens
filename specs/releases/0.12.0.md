## pageslens 0.12.0

Parent chains in policies: say which parent a child table has to be reached through, so a policy can check "signed-in users read the tasks of their own incidents, and no other tasks". Plus recipes for an ALM workflow and for Azure Pipelines.

### New

- **`under` and `except under` in access statements.** A child (Parent scope) permission gives access to the rows related to the rows its parent gives. Until now a policy could say a grant is at `parent scope`, but not what the parent is, so tasks under "my incidents" and tasks under every incident looked the same. Now a statement can name the chain:

  ```yaml
  access:
    - authenticated can read incident at contact scope
    - authenticated can read task under incident at contact scope
    - authenticated cannot read task except under incident at contact scope
  ```

  `under <table> [at <scope> scope]` counts only grants whose parent chain has a permission on that table, at any depth: the nearest one counts, at that scope when one is given. It works in all four forms. `except under …` leaves those grants out, so the statement is about every other way to reach the table; it goes in `cannot`, `only` and `nobody`. The third line above fails for any signed-in role that reaches tasks another way, such as under an incident permission at global scope, or under a permission on another table:

  ```
  FAIL  authenticated cannot read task except under incident at contact scope  (line 3)
        Staff has read on task (parent scope) from "Incident Task - All Staff", under "Incident - All Staff" (incident, global scope)  table-permissions/Incident-Task-All-Staff.tablepermission.yml
  ```

  Chains are the ones the access matrix in `docs` shows: child permissions with no web role take their parent's, and a broken chain grants nothing. See "Parent chains" in [docs/policy.md](https://github.com/OOlashyn/pageslens/blob/main/docs/policy.md).

- **Recipes for an ALM workflow** ([docs/alm.md](https://github.com/OOlashyn/pageslens/blob/main/docs/alm.md)): pull request validation, nightly environment drift, release notes and the checks to run before a release, for the layout the Power Platform ALM white paper uses.

- **Azure Pipelines** ([docs/azure-devops.md](https://github.com/OOlashyn/pageslens/blob/main/docs/azure-devops.md)): a pipeline for a repository in Azure Repos that does what the GitHub Action does, in script steps: `lint`, `test`, `align` and `diff`, the access changes on the run's summary and as a pull request comment, and optionally SARIF for GitHub Advanced Security for Azure DevOps. There's no Marketplace task yet.

### Changed

- **A grant through a parent chain names where the chain starts.** In `test` and `diff`, `under "<top parent>"` now gives the top permission's table and scope, so you can see which rows the chain starts from without opening its file:

  ```
  Customers gained read on annotation (parent scope) from "Case Note - Customers", under "Case - Customers" (dwcrm_case, contact scope)
  ```

### Upgrading

Policies that don't use `under` or `except under` pass and fail as in 0.11.0. In earlier versions, a statement using them was an unreadable statement (exit code `2`).

The wording of parent-chain grants changed in `test` and `diff` output, the pull request comment and SARIF messages. If you match on that text, update the pattern. The JSON outputs' `version` is still 1.

```bash
npm install --save-dev pageslens@0.12.0
```

Update the action to `OOlashyn/pageslens@v0.12.0`.
