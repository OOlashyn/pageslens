## pageslens 0.8.0

Unpacked solutions: pageslens now reads the solution that holds a site, so teams that keep the solution in git get `lint`, `test`, `diff` and `docs` on what they deploy. Also settings from environment variables, a lint rule for Web API inner errors, and unused ignore entries.

### New

- **Unpacked solutions.** Point any command at the folder `pac solution unpack` writes (the one with `Other/Solution.xml`) or at the project `pac solution clone` writes (pageslens looks in its `src/`):

  ```bash
  npx pageslens lint solution/MySolution
  ```

  Each component in `powerpagecomponents/<guid>/` is read into the same records as a download of the same site, matched by GUID, so the findings, policy results and docs are the same; on the two sites it was checked on, record for record. Findings point at the component's `powerpagecomponent.xml`. `diff` compares two solutions (two commits of the solution folder, the usual pull request), or a solution with a download. A code site and a classic site are told apart by `CodeSite/Enabled`. A solution with more than one site, the YAML source control format (Dataverse Git integration) and solution `.zip` files aren't read yet. See the [README](https://github.com/OOlashyn/pageslens#solutions).

- **Settings from environment variables.** A site setting can take its value from an environment variable. In a solution, pageslens reads the variable's current value, or else its default, and says where it came from: `ASP/Pagination/CardsPerPage is "20" from environment variable dwcrm_CardsPerPage`.
- **`webapi-inner-errors`** (warning). `Webapi/error/innererror = true` makes a failed Web API call return the server error behind it. That helps in development, and Microsoft's Web API walkthrough turns it on, but on a live site it tells anyone who calls the API more than they need. Set it to `false` or remove it outside development. See [rules/webapi-inner-errors.md](https://github.com/OOlashyn/pageslens/blob/main/rules/webapi-inner-errors.md).
- **Unused ignore entries.** `lint` lists each `files` glob or `records` GUID in a `pageslens.config.yaml` ignore entry that left out no finding, under the config file's name, so an entry for something since fixed doesn't hide the next finding there:

  ```
  pageslens.config.yaml
    warning  Ignore entry 2: file "web-roles/Legacy-*.webrole.yml" matches no finding; remove it if what it ignored is fixed.

  4 errors, 0 warnings, 0 info, 1 ignored, 1 unused ignore
  ```

  They don't fail the run and aren't in SARIF. An entry that lists a rule that's turned off isn't checked. In JSON they're the new `unusedIgnores` field (`entry`, counted from 1, `field` and `value`).

### Fixed

- **Settings from environment variables in a download.** A download has such a setting's leftover value, which the site doesn't use, and nothing of the variable. Every release so far read the leftover value, so a policy could pass, or a wider change go unreported, on a value the site doesn't have. Now the value is unknown: lint rules that need it skip the setting, a `test` statement that needs it fails and says why, `diff` counts a move to a variable as wider, and the Web API page in `docs` shows it as unknown. Check those values against the solution.

### Upgrading

Sites with `Webapi/error/innererror = true` get one more warning, and a new code scanning alert if you upload SARIF. Warnings don't change the exit code. To keep the setting on a development site, ignore its record in that site's `pageslens.config.yaml`, or set the rule to `off`.

On a download where a setting takes its value from an environment variable, `test` may now fail and `diff --fail-on wider` may fail where they passed. `Webapi/<table>/enabled` from a variable also takes that table out of the Web API lint rules for the download.

The JSON outputs' `version` is still 1: `unusedIgnores` (`lint`) and each side's `format` (`diff`: `code-download`, `classic-download` or `solution`) are added fields.

