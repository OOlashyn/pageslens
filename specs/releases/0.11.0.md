## pageslens 0.11.0

Deployment settings: give `lint`, `test`, `diff` or `align` one stage's deployment settings file, and settings backed by environment variables get the values that stage will receive, instead of `unknown` in a download or dev's value in a solution.

### New

- **`--settings <file>` on `lint`, `test`, `diff` and `align`.** The values of environment variables differ per stage, and the import takes each stage's values from a deployment settings file: the JSON `pac solution create-settings` writes and `pac solution import --settings-file` reads, usually kept in the repository as `deployment-settings/<stage>.json`. The settings that matter most per stage (`Webapi/<table>/enabled`, `Webapi/<table>/fields`, `Authentication/Registration/Enabled`) are often the ones backed by a variable, so now they can be checked where it counts:

  ```bash
  npx pageslens lint site --settings deployment-settings/prod.json
  npx pageslens test site --settings deployment-settings/prod.json
  ```

  A setting backed by a variable takes the file's `Value` for it, matched by schema name, ignoring case, and is checked like any other setting: the `webapi-*` rules that skipped an unknown value now check it, and `test` statements pass or fail on it. Messages name the file:

  ```
  "true" from environment variable dwcrm_ContactApi in deployment-settings/prod.json
  ```

  It works on a download and on a solution alike. Only `EnvironmentVariables` is read; connection references, `DefaultValue` and variables no setting uses are ignored. One stage per run: check several stages with several runs.

- **Unknown stays unknown.** A variable the file doesn't have, or has with an empty `Value` (as `create-settings` writes every variable), keeps what it had: unknown in a download, the solution's value in a solution. So does a secret (`TypeId` 100000005), whose value is in Azure Key Vault. pageslens doesn't guess what the import does then, and the message says what the file has:

  ```
  Authentication/Registration/Enabled comes from environment variable dwcrm_Registration, which a download doesn't include, and deployment-settings/test.json gives it no value
  ```

- **`diff` reads the file on each side**: from the folder, or at the same path in each commit. A pull request that only changes a stage's file now shows what it does to access:

  ```bash
  npx pageslens diff origin/main HEAD --site site --merge-base --settings deployment-settings/prod.json
  ```

  ```
  Wider
    + the Web API is now enabled on contact; callers: Authenticated Users (read)
        site-settings/Webapi-contact-enabled.sitesetting.yml
  Narrower
    - Authentication/Registration/Enabled turned off: was "true" from environment variable dwcrm_Registration in deployment-settings/prod.json at origin/main, now "false" from environment variable dwcrm_Registration in deployment-settings/prod.json at HEAD
        site-settings/Authentication-Registration-Enabled.sitesetting.yml
  ```

  A side without the file reads it as empty, so a new stage's file shows as a change. See [docs/diff.md](https://github.com/OOlashyn/pageslens/blob/main/docs/diff.md).

- **`align` checks the variables against the file.** `variable-no-value` isn't reported when the file gives the variable a value. A new warning, `variable-not-in-settings`, reports a variable that has a value in the solution and none in the file: a value in the solution goes with it, so the stage may get dev's. An unedited `create-settings` file warns on each such variable, which is the point. See [docs/align.md](https://github.com/OOlashyn/pageslens/blob/main/docs/align.md).

- **The GitHub Action's `settings` input** passes `--settings` to every command it runs:

  ```yaml
  - uses: OOlashyn/pageslens@v0.11.0
    with:
      path: site
      settings: deployment-settings/prod.json
  ```

  To check several stages, run the action once per stage (a matrix). Each run edits the same pull request comment, so turn `comment` off on all but one.

### Upgrading

Nothing changes unless you give `--settings` (or the action's `settings` input): every command gives the same output and exit code as 0.10.0. A file that can't be read, isn't JSON, or has no `EnvironmentVariables` list of entries with a `SchemaName` is exit code `2`.

With a file, rules and statements that skipped or failed on an unknown value now check the stage's value, so `lint` can find new errors and `test` can pass or fail where it didn't. `variable-not-in-settings` is a new check in the config schema; turn it off with `align.checks` if you don't want it. The JSON outputs' `version` is still 1, and SARIF hasn't changed.

```bash
npm install --save-dev pageslens@0.11.0
```

Update the action to `OOlashyn/pageslens@v0.11.0`.
